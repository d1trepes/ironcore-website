# Порядок работы: ChatGPT → GitHub → Claude → WordPress

## Основной принцип
**1 небольшой чат = 1 законченная задача.** Не открывать новый чат после каждого клика. Новый чат открывается, когда утверждена и зафиксирована одна логическая часть, и контекст начинает разрастаться. В GitHub должно оставаться достаточно информации для следующего чата без пересказа истории.

## Этапы ChatGPT (арт-дирекшн)
- **00 / Проверка стартовых материалов:** новый чат читает `docs/PROJECT_STATE.md`, `docs/brief.md`, `docs/content.md`, `docs/tz-checklist.md`, `docs/visual-direction.md`, проверяет доступ к GitHub, предлагает короткий план следующих действий. НЕ тратит время на повторную расшифровку скриншотов.
- **01 / Логотип:** по `docs/logo-brief.md` подготовить 3 **различные** SVG-концепции, согласовать один основной, альтернативы сохранить отдельно. При утверждении обновить docs/design-system.md и статус.
- **02 / Структура:** сравнить `docs/page-blueprint.md` с `docs/content.md` и чек-листом, принять финальную компоновку 11 разделов; записать решения. Не уходить в дебаты по каждой мелочи.
- **03 / Визуальное направление:** превратить компромисс двух первых экранов в 1–2 конкретные композиции, обсудить с дизайнером, зафиксировать утверждённый hero и остальные секции. При запросе визуализировать конкретный блок статичной картинкой; это исследование, не замена кодовой спецификации.
- **04 / Передача Claude:** привести `CLAUDE.md` и docs в соответствие с утверждённым видом, подготовить короткое стартовое сообщение, проверить отсутствие конфликтов.
- **05 / QA:** проверить готовое демо, адаптив, навигацию, контент и ТЗ; записывать исправления в GitHub, затем передать разработчику.

## Этапы Claude (реализация)
Работать по коротким шагам. Не давать Claude абстрактную задачу «сделай уникальный сайт»: конкретный документ + конкретный диапазон блоков + результат.
- **Код 01**: каркас, шапка, футер, форма-заглушка и утверждённый hero.
- **Код 02**: разделы 02–03.
- **Код 03**: разделы 04–05.
- **Код 04**: разделы 06–07.
- **Код 05**: разделы 08–11.
- **Код 06**: мобильная адаптация, состояния, доступность и проверка.
- Дальше — точечные правки по результатам просмотра.

## Протокол конца КАЖДОГО чата
1. Записать фактически сделанные и **утверждённые** изменения в нужные файлы GitHub.
2. Обновить `docs/PROJECT_STATE.md`: выполнено, принято, требует решения, задача следующего чата, ссылки на файлы и коммит.
3. Проверить, что commit/push действительно выполнены (если есть право записи); иначе честно указать, что в GitHub не сохранено.
4. Ответ не длиннее 6–10 строк: краткий итог, что осталось, **полная ссылка на репозиторий**, ссылка на изменённый файл/коммит, стартовый промпт нового чата.
5. Новый чат сначала читает **ровно** `README.md`, `docs/PROJECT_STATE.md` и необходимые файлы для своей задачи; не перебирает весь репозиторий без нужды.

## Экономия токенов
- Не перепечатывать всё ТЗ в каждом чате. Источник = `docs/content.md`. Для шага читать нужный раздел, не все 11, если не нужен аудит.
- Не использовать внешние нейросети для выдумывания технических цифр и преимуществ.
- При исправлении — редактировать конкретный файл и блок, не переписывать весь сайт без необходимости.
- Не делать много концепций одновременно, кроме явно запрошенных 3 логотипов.
- Не устанавливать фреймворк, сборщик или пакеты без ясной причины; предпочтение чистым HTML/CSS/JS.
- После первого рабочего демо проверять именно проблемы, а не бесконечно полировать незаметные детали.

## Передача разработчику WordPress
Из репозитория можно использовать готовые HTML/CSS/JS-компоненты, SVG, изображения, документацию, текст и состояния. WordPress-разработчик отдельно решает шаблоны, редактирование контента, отправку заявки/Telegram, хранение файлов, юридические документы, хостинг. Делать второй репозиторий не обязательно; отдельную ветку/форк WordPress-разработчик может создать по желанию.

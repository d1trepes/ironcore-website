# IRONCORE — маршрут разработки и согласования в Claude

Дата: 2026-11-10. Этот документ описывает ПОРЯДОК работы, а не заменяет проектное ТЗ и макет. GitHub — единый актуальный источник, Claude — исполнитель кода. Один проект в Claude, отдельный чат на каждый этап. При необходимости этап 02 можно повторять несколькими короткими чатами.

## Подготовка владельца проекта (однократно)
1. Создать проект Claude с названием «IRONCORE — Website».
2. В поле Project Instructions вставить docs/claude-project-instructions.md. Сохранить.
3. Подключить рабочую среду Claude Code к d1trepes/ironcore-website (или дать Claude доступ к GitHub и возможность записывать изменения). Проверить реальную возможность читать и писать: просто доступ к веб-ссылке не равен доступу на запись. Если Claude работает лишь в веб-чате без исполнения кода, передавать задачи исполнителю в Claude Code; не представлять текстовый ответ как опубликованный сайт.
4. Не копировать все 24 скриншота ТЗ в каждый чат: полный текст уже в docs/content.md. Не создавать новый репозиторий и не работать в ironcore-landing/ironcore-hero.

## Общее правило новых чатов
В начале каждого: «Прочитай README.md, docs/PROJECT_STATE.md, CLAUDE.md из d1trepes/ironcore-website, затем материалы своего этапа. Назови текущую стадию и приступи к конкретному заданию». GitHub сохраняет контекст лучше истории предыдущего чата. В проектной базе знаний можно хранить инструкции, но при расхождении с GitHub приоритет у актуального GitHub.

## Чат 01 — DESKTOP / первая версия
Цель: работающий полный 11-секционный desktop-сайт, а не отдельный hero. Читаем весь docs/content.md, docs/page-blueprint.md, docs/tz-checklist.md и дизайн-документы. Реализуем 1440 и 1024 px, шапку/якоря, 6 рисков, 3 масштаба с точными цифрами, 4 формата, 6 услуг, 6 этапов, 4 инженерных темы с расчётами, 7 FAQ, форму, футер. На узких экранах хотя бы нет разрушения верстки, но финальный mobile выполняется на этапе 03. Использовать только имеющиеся безопасные архитектурные ассеты; недостающие реальные рендеры фиксировать в docs/asset-manifest.md с описаниями/размерами, показывать честные плейсхолдеры, а не изображать несуществующие картинки как готовые. Реально работающая навигация/переключатели/модалки/аккордеоны. Демо отправки заявки ясно обозначено как демо.
Выход: код + локальный preview (или доступный способ его открыть) + коммит + проектный статус. Состояние: desktop «на ревью», НЕ утверждён. Стоп — ждать отзыв пользователя.

## Чат 02 — DESKTOP REVISIONS / дизайнерские правки
Цель: исправлять только названные пользователем детали. Начать с просмотра реально существующего кода, текущей версии и docs/PROJECT_STATE.md. Попросить пользователя описать замечания ТОЛЬКО если замечаний в текущем запросе нет; при наличии текста/скринов выполнять сразу. Сначала кратко сформулировать затрагиваемые блоки, затем исправить. Не подменять утверждённые тексты/цифры и не менять все разделы ради одной правки. При необходимости повторять отдельным чатом «02b / доработки». Desktop становится «утверждён» лишь после явных слов пользователя об одобрении. Фиксировать точные решения в docs/PROJECT_STATE.md и соответствующем design-файле, commit/push. Не начинать мобильную сборку без подтверждения.

## Чат 03 — MOBILE / адаптация после desktop-approval
Цель: полноценно адаптировать принятый desktop к 768, 390, 360 px, также проверить 1024 px. Сохранить desktop дизайн. Mobile: шапка и меню, контент hero перед визуалом, адаптированный кадр архитектуры; 6 рисков вертикально; масштабы с тремя цифрами каждый; 4 формата; услуги и инженерные темы в доступных аккордеонах; 6 этапов и FAQ; форма; футер. Не скрывать обязательные сведения. Проверить горизонтальное переполнение, удобство тача, фокус, модальные окна, таблицы, длину русского текста. Внести код, открыть mobile-preview, коммит и статус. Стоп — ждать визуальное одобрение мобильной версии.

## Чат 04 — QA / финальная проверка
Цель: проверка всей страницы на 1440, 1024, 768, 390, 360 px. Проверить каждый пункт docs/tz-checklist.md, все якоря, CTA, вкладки, модалки, закрытие по Escape, фокус, формы и ошибки, FAQ, корректность изображений, отсутствие воды/чужих логотипов, точность всех цифр, контраст, prefers-reduced-motion, отсутствие ложных функций Telegram/PDF, скорость и браузерные ошибки. Для каждого найденного дефекта указать влияние и исправить. Не менять дизайн без согласования. Чек-лист отмечать «сделано» только по реально проверенным пунктам. Выход — QA-отчёт в docs/qa-report.md, коммит, статус «готово к презентации» только при устранении критичных проблем.

## Чат 05 — PRESENTATION / презентация
Цель: подготовить демо для посредника и заказчика. Проверить preview/публичную ссылку; если публикация требует доступа к хостингу, описать конкретный шаг и не выдумывать URL. Подготовить короткий презентационный сценарий: 1) первый экран и позиционирование; 2) защищённость; 3) концепции; 4) услуги/инженерия; 5) заявка, desktop/mobile. Сделать docs/presentation-notes.md с сильными сторонами, честным списком того, что в демо и что включат на WordPress (Telegram, PDFs, политика, реквизиты). Подготовить docs/wordpress-handoff.md: дерево файлов, ассеты, интерактивные состояния, формы, интеграции, потребности в лицензиях, инструкция запуска. Не выдавать демо за полностью запущенный коммерческий сайт. Заключительный коммит и PROJECT_STATE.

## Правила коммитов и статуса
- Коммитить завершённые изменения каждого чата в основной рабочий репозиторий либо в отдельную рабочую ветку с понятным способом слияния, если прямой push не разрешён. Не создавать новый репозиторий.
- docs/PROJECT_STATE.md хранит: текущий этап, готово, утверждено пользователем, не готово, известные ограничения, следующую команду.
- При большой правке обновлять docs/page-blueprint.md только если пользователь действительно согласовал изменение структуры; не переписывать ТЗ.
- Все PDF, исходные изображения, формы с реальными отправками и внешние связи требуют фактических файлов или доступов. Отсутствие не скрывать.
